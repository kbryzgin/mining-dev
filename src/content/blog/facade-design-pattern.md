## Паттерн Фасад на примере работы с Micromine Python API

При разработке скриптов автоматизации или встраиваемых программных модулей для ГГИС Micromine 
мы часто последовательно обращаемся к нескольким объектам и методам API.

Например, чтобы прочитать имена полей из DAT-файла, необходимо создать объект `MMpy.File`, открыть файл,
узнать количество полей, последовательно прочитать их, используя идентификатор поля и закрыть файл.

Каждая из этих операций сама по себе несложная, но если такую последовательность приходится повторять
в разных частях скрипта, то код начинает дублироваться, а прикладная логика начинает обрастать деталями
работы с API.

Один из способов решить эту проблему - применить паттерн **Фасад**.

## 1. Что такое паттерн Фасад

Фасад - структурный паттерн проектирования, который предоставляет упрощенный интерфейс к сложной подсистеме.

Прикладному коду не обязательно знать обо всех внутренних объектах подсистемы, порядке вызова методов и особенностях их взаимодействия. 
Фасад координирует эти действия и предоставляет вызывающему коду более понятную операцию высокого уровня.

## 2. Пример без использования Фасада

Допустим, перед нами стоит задача прочитать имена полей из файла ввода и передать их в виде списка в функцию `print()` для вывода.

В такой задаче, без использования паттерна **Фасад**, можно выделить несколько компонентов:

```text
Клиентский код/бизнес-логика
      |
      v
  Объекты API
      |
      v
   Micromine
```

Пример реализации:

```python
import MMpy


file_path = "bm.DAT"
fields = []

file = MMpy.File()

file.open(file_path)	
for i in range(file.structure.fields_count):
	fields.append(file.structure.get_field_name(i))

file.close()

print(fields)
```

Код выполняет задачу, но прикладная логика напрямую зависит от последовательности вызовов `MMpy`.

Если чтение имен полей файла потребуется в нескольких местах скрипта, эту последовательность придется повторять. 
Если изменится логика чтения данных или появятся дополнительные проверки, например проверка корректности открытия файла или управление ресурсами, изменения также придется вносить 
в несколько участков кода.

```python
import MMpy


file_path = "bm.DAT"
fields = []

file = MMpy.File()

# Проверку необходимо будет добавлять во все участки кода, где есть логика чтения
if not file.open(file_path):
	raise IOError(f"Ошибка: не удалось открыть файл: {file_path}")

try:
	for i in range(file.structure.fields_count):
		fields.append(file.structure.get_field_name(i))

finally:
	file.close()

print(fields)
```

Это не означает, что прямое использование API является ошибкой. Для небольшого одноразового сценария оно вполне оправдано. 
Проблема возникает тогда, когда одна и та же техническая последовательность становится повторяющейся частью приложения.

## 3. Пример с использованием Фасада

Если, при решении данной задачи мы будем использовать паттерн **Фасад**, то в нашей архитектурной схеме добавится еще один компонент:

```text
Клиентский код/бизнес-логика
      |
      v
    Фасад
  get_fields()
      |
      v
  Объекты API
      |
      v
   Micromine
```

Реализация:

```python
import MMpy


def get_fields(file_path: str) -> list:
	"""Упрощенный интерфейс (фасад) для чтения имен полей из файла."""
	file = MMpy.File()
	if not file.open(file_path):
		raise IOError(f"Ошибка: не удалось открыть файл: {file_path}")

	try:
		fields = []
		for i in range(file.structure.fields_count):
			fields.append(file.structure.get_field_name(i))
		
		return fields

	finally:
		file.close()
		

# Клиентский код
file_path = "bm.DAT"
fields = get_fields(file_path)
print(fields)
```

Теперь исходная задача выглядит проще, а если нам потребуется изменить логику чтения полей из файла, то правки нужно будет 
вносить только в одном месте, в функции `get_fields()`. При этом мы можем вынести функцию get_fields() в отдельный модуль, изолировав в нём компоненты, зависящие от API. 
В результате прикладная логика не будет напрямую зависеть от MMpy: ей не потребуется импортировать эту библиотеку.
Главное изменение заключается не в сокращении количества строк кода само по себе, а в разделении ответственности.

Фасад не обязательно должен быть реализован в виде функции, изолирующей низкоуровневые операции API. В роли фасада может выступать 
класс и даже модуль. Основной смысл паттерна заключается в предоставлении упрощённого интерфейса высокого уровня для взаимодействия со сложной подсистемой.

## Заключение

При разработке программных модулей для ГГИС фасад позволяет отделить прикладную логику от особенностей конкретного API. 
Вместо того чтобы распределять вызовы MMpy по всему проекту, мы можем сосредоточить взаимодействие с Micromine в отдельных компонентах и предоставить остальной части приложения понятный интерфейс.

Это упрощает сопровождение программного модуля, уменьшает связанность компонентов и создаёт основу для дальнейшего развития архитектуры.
